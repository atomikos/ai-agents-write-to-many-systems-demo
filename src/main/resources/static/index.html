How it works

four calls, as an agent chains four tools - each commits on its own
① mark the order refunded → PostgreSQL
② publish RefundIssued → Artemis · queue "refund.events"
③ add the refund note → CRM over HTTP
④ send the confirmation email

Don't do this. A failure or a crash leaves the earlier steps in place, and every call is a new refund, so calling again refunds again.

refund(refundId, orderId)
first, record the intent → PostgreSQL · saga row PENDING
③ add the refund note → CRM over HTTP, idempotency key = refundId · before the others, so a refusal leaves nothing to undo
① mark the order refunded, saga row COMPLETED → PostgreSQL
② publish RefundIssued → Artemis · queue "refund.events"
④ request the confirmation email → Artemis · queue "email.requests"
Dashed box = one XA transaction: all three commit together, or none does.
↓  only after commit
BillingListener books the refund · EmailSender sends the email

Step numbers as in the article. The CRM cannot join the transaction. If anything fails after step ③, the compensator reverts the note by its key; after a crash, a sweep does the same once the refund has been PENDING for 30 seconds.
